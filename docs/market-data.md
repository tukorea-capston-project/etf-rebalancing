# 시세·분배금 데이터 수집 설계

백테스트에 쓰는 ETF 일별 시세(KRX Open API)와 분배금 이력(yfinance)을 수집해 DB에 저장하는 방법을 정의한다.
코드 구현은 `backend/app/market_data/`에 둔다. 출처별 구현은 분리해, 나머지 코드를 고치지 않고 출처만 교체할 수 있게 한다.

## 수집 대상

- 화이트리스트(`backend/config/etf_whitelist.yaml`)의 ETF와 KODEX 200(`069500`, 백테스트 비교 기준)만 저장한다.
- KRX는 호출 한 번에 그날의 전체 ETF를 돌려준다. 그중 대상 ETF만 골라 저장한다.
- 기간은 2010-01-01부터 수집하는 날까지다. KRX 데이터가 2010년 이후만 있다.

## 시세 (KRX Open API, ETF 일별매매정보)

### 저장 필드

응답 필드를 거의 전부 저장한다. 나중에 거시판단이나 슬리피지 모델에 쓸 수 있고, 필드를 추가하려고 전 기간을 다시 수집하지 않기 위해서다.

| 분류 | KRX 필드명 | 내용 |
|---|---|---|
| 식별 | `BAS_DD` / `ISU_CD` / `ISU_NM` | 기준일자 / 종목코드 / 종목명 |
| 가격 | `TDD_CLSPRC` / `CMPPREVDD_PRC` / `FLUC_RT` | 종가 / 전일대비 / 등락률 |
| | `TDD_OPNPRC` / `TDD_HGPRC` / `TDD_LWPRC` | 시가 / 고가 / 저가 |
| 거래 | `ACC_TRDVOL` / `ACC_TRDVAL` | 거래량 / 거래대금 |
| 규모 | `MKTCAP` / `INVSTASST_NETASST_TOTAMT` / `LIST_SHRS` | 시가총액 / 순자산총액 / 상장좌수 |
| NAV·지수 | `NAV` / `IDX_IND_NM` | NAV / 기초지수명 |
| | `OBJ_STKPRC_IDX` / `CMPPREVDD_IDX` / `FLUC_RT_IDX` | 기초지수 종가 / 전일대비 / 등락률 |

- 응답 필드는 모두 문자열이다. 숫자 필드는 숫자로 변환하고, 빈 값이나 `-`는 null로 저장한다.
- 종목코드는 6자리 문자열 그대로 둔다. 최근 상장 종목은 영문 대문자가 섞여 있다(예: `0184E0`).
- 종목명은 날짜별 행에 저장한다. 운용사 브랜드 변경 등으로 이름이 바뀌어도 그날의 이름이 남는다.

### 응답 형태

- 응답은 `{"OutBlock_1": [...]}`이며, 행마다 19개 필드가 모두 문자열로 온다.
- 영업일: 그날 상장된 ETF마다 한 행이 오고 종가 등에 값이 있다.
- 휴장일: 행은 오지만 가격·거래·NAV·지수 값이 모두 빈 문자열이다. 종목명, 상장좌수, 기초지수명만 값이 있다.
- 아직 제공되지 않은 날짜: 빈 목록이 온다.
- 인증 오류: HTTP 401, `{"respMsg": "Unauthorized Key", "respCode": "401"}`. 하루 한도 초과 응답의 형식은 확인하지 못했다.
- 2010년 초에는 기초지수 값이 비어 있는 ETF가 있다.

### 수집 이력

호출한 날짜마다 결과를 **수집 이력 테이블**에 기록한다.

| 결과 | 의미 | 다음 실행 때 |
|---|---|---|
| 영업일 | 종가가 있는 행이 왔다 | 다시 호출하지 않는다 |
| 휴장일 | 종가가 모두 빈 행이 왔다, 또는 유예 기간이 지난 날짜에 빈 목록이 왔다 | 다시 호출하지 않는다 |
| 대기 | 유예 기간 안의 날짜에 빈 목록이 왔다 | 다시 호출한다 |
| 실패 | 오류·한도 초과 등 | 다시 호출한다 |

- 최근 14일(유예 기간, 설정값) 안의 빈 목록은 휴장일로 확정하지 않고 대기로 기록한다. 당일 데이터는 다음 영업일에 제공되고, 연휴 등으로 제공이 늦어질 수 있기 때문이다. 다음 실행 때 다시 확인하고, 유예 기간이 지난 날짜의 빈 목록은 휴장일로 확정한다.
- 수집 이력의 영업일 목록은 **과거 영업일 달력**으로도 쓴다. 미래 영업일 달력은 주문 방식 설계(#13)에서 정한다.

### 신규 ETF 자동 감지

- ETF마다 전 기간 수집을 마쳤는지 기록한다(백필 완료 기록).
- 화이트리스트(와 KODEX 200)에 백필 완료 기록이 없는 ETF를 신규 ETF로 본다.
- 신규 ETF가 있으면, **이번 실행을 시작하기 전에 이미 영업일로 기록돼 있던 날짜**만 다시 호출해 그 ETF의 과거 데이터를 채운다.
  - 이번 실행에서 새로 받는 날짜는 이미 신규 ETF를 포함하므로 다시 호출하지 않는다.
  - 다시 받을 영업일이 없으면(초기 적재) 호출 없이 실행 시작 때 바로 완료로 기록한다. 초기 적재에서 화이트리스트 ETF가 모두 신규로 판정돼도 같은 날짜를 두 번 호출하지 않는다.
  - 영업일은 약 4,000일이고, 실행당 상한(9,000회) 안에 끝난다. 한 번 호출에 전체 ETF가 오므로, 새 ETF가 여러 개여도 한 번에 채워진다.
  - 다시 받은 응답에서는 **신규 ETF 행만** 저장한다. 이미 있는 시세는 덮어쓰지 않아, ETF를 추가해도 기존 ETF의 백테스트 입력이 바뀌지 않는다.
  - 모든 날짜를 받아야 완료로 기록한다. 중간에 실패하거나 멈추면 다음 실행 때 처음부터 다시 받는다.

### 상장일

- ETF의 상장일은 DB에서 그 ETF의 시세가 처음 나타나는 날로 본다. 백테스트의 공통 시작일 계산에 쓴다.
- 첫 데이터가 2010년 첫 영업일이면 2010년 이전 상장이다. 이 경우 데이터 시작일부터 쓸 수 있다고 본다.

### 시세가 없는 날

장이 열린 날인데 특정 ETF만 시세가 없으면(거래정지 등) 아래처럼 처리한다.

- 평가는 직전 종가로 한다.
- 그날 체결 예정이던 그 ETF의 주문은 시세가 다시 생기는 날 체결한다.
- 다른 ETF의 주문은 예정대로 체결한다.

### 호출 제한과 실패

- 인증키당 하루 10,000회 한도를 넘지 않도록 두 가지로 막는다. 남은 날짜는 수집 이력에 남아 다음 실행 때 이어서 받는다.
  - 한 번 실행할 때의 최대 호출 수를 설정값(기본 9,000회)으로 두고, 도달하면 멈춘다.
  - 오류 응답(HTTP 오류, `respCode` 오류)을 받으면 한도 초과인지 구분하지 않고 재시도 없이 바로 멈춘다. 한도 초과 응답의 형식을 확인하지 못했고, 인증·한도·서버 오류는 날짜를 바꿔도 계속 나므로 호출을 낭비하지 않는다. 같은 날 여러 번 실행해 실행당 상한으로는 막지 못한 경우도 이것으로 막는다.
- 네트워크 오류(연결 실패, 타임아웃)는 1·2·4초 간격으로 3번 다시 시도한다(타임아웃 30초, 설정값). 그래도 실패하면 그 날짜를 실패로 기록하고 다음 날짜로 넘어간다.
- 이미 저장된 시세 행은 덮어쓰지 않는다.
- 호출 간격은 설정값으로 두고 기본값은 0.5초다. 초당 호출 제한은 공개 문서에서 확인하지 못해 보수적으로 잡았다. 초기 적재(약 6,000회)의 대기 시간은 약 50분이다.
- 공용 개발 DB(AWS)에는 한 곳에서만 수집한다. 지금은 담당 팀원이 수동으로, 나중에는 EC2의 워커(`docs/architecture.md`)가 수집한다. 여러 곳에서 동시에 수집하면 수집 이력이 꼬이고 호출 한도도 낭비된다.
- KRX 인증키(`.env`의 `KRX_API_KEY`)는 수집하는 쪽의 것을 쓴다. 로컬 개발 DB에 따로 받을 때는 자기 인증키를 쓴다.

## 분배금 (yfinance)

- 공식 출처로는 2010년부터의 ETF 분배금 이력을 받을 방법이 없어 yfinance를 쓴다.
  - 공공데이터포털 배당 API: ETF 분배금이 없다.
  - SEIBro: 페이지마다 수동으로 받아야 한다.
  - KIND: 공시 문서를 하나씩 파싱해야 한다.
- 티커는 `<종목코드>.KS`다. 날짜는 분배락일이고, 금액은 주당 분배금(세전)이다.
- 수집할 때마다 대상 ETF별로 **전체 분배금 이력을 다시 받아** 그 ETF의 yfinance 분배금을 갱신한다. 야후가 나중에 고친 값도 반영된다.
- 아래 경우에는 그 ETF를 갱신하지 않고 기존 값을 유지한 뒤 경고를 남긴다. yfinance 장애 한 번에 분배금 이력이 지워져 백테스트 결과가 바뀌는 것을 막는다. 보정 YAML은 이때도 적용한다.
  - 재시도(1·2·4초 간격 3번) 후에도 받지 못했다.
  - 0건이 왔는데 DB에는 그 ETF의 yfinance 분배금이 있다. 정말 지워야 하는 값은 보정 YAML의 `delete`로 지운다.
- 분배금이 원래 없는 ETF(TR ETF 등)는 0건이 정상이므로 경고하지 않는다.
- ETF 하나가 실패해도 나머지 ETF는 계속 갱신한다.

### 보정 파일

- yfinance의 누락·오류는 저장소에 커밋한 **보정 YAML**(`backend/config/distribution_overrides.yaml`)로 고친다.
- DB를 직접 고치지 않는다. 직접 고친 값은 다음 수집 때 yfinance 값으로 덮여 사라지고, 로컬 개발 DB를 쓰는 팀원과 백테스트 결과가 달라진다.
- 수집할 때 yfinance 데이터 위에 보정 YAML을 덮어 적용한다.
- 보정 YAML의 요구 사항
  - 분배금 추가, 금액·날짜 수정, 잘못된 항목 삭제를 표현할 수 있어야 한다.
  - 항목마다 근거(KIND 공시 URL 등)를 적는다.
  - 종목코드는 따옴표로 감싼 6자리 문자열로 쓴다.
- 형식은 (종목코드, 분배락일)별 **최종값**을 적는 방식이다.
  - 금액(`amount`)을 적으면 그 값으로 추가하거나 수정한다.
  - `delete: true`를 적으면 그 항목을 지운다.
  - 날짜를 고칠 때는 잘못된 날짜의 삭제 항목과 맞는 날짜의 추가 항목, 두 개를 쓴다.
  - `source`(근거)는 모든 항목에 필수다.
  - 같은 (종목코드, 분배락일)이 두 번 나오면 오류로 본다.
  - 수집 대상(화이트리스트와 KODEX 200)이 아닌 종목코드가 있으면 오류로 본다.
  - 정의하지 않은 키(예: 오타 `delet`)가 있으면 오류로 본다.

  ```yaml
  overrides:
    # 누락 추가 또는 금액 수정
    - code: "069500"
      ex_date: 2015-04-29
      amount: 150
      source: https://kind.krx.co.kr/...
    # 잘못된 항목 삭제
    - code: "069500"
      ex_date: 2015-04-30
      delete: true
      source: https://kind.krx.co.kr/...
  ```

- 처음에는 비어 있다. 공식 출처와의 대조는 보류했다(이슈로 관리).

## 수집 명령

- 수집 로직은 `backend/app/market_data/service.py`에 둔다. 나중에 워커가 매일 자동 수집할 때도 같은 함수(`run_collection`)를 부른다.
- 출처는 `krx.py`(시세), `yahoo.py`(분배금)에 두고, `service.py`는 출처 인터페이스(Protocol)로만 다룬다. 출처를 바꿔도 `service.py`는 고치지 않는다.
- 지금은 터미널 명령(CLI)으로 수동 실행한다. `backend/`에서 `uv run python -m app.market_data`로 실행한다. 명령이 하나뿐이라 의존성을 늘리지 않고 표준 라이브러리 argparse로 만든다.
- 한 번 실행하면 아래를 차례로 한다.
  1. 수집 이력에 없거나 대기·실패로 남은 날짜의 시세 수집
  2. 신규 ETF가 있으면 이번 실행 전 영업일 재수집
  3. 대상 ETF의 분배금 전체 이력 갱신 + 보정 YAML 적용
- KRX 오류나 호출 상한으로 1·2가 멈춰도 3은 진행한다. 출처가 다르기 때문이다.
- 실패·중단·경고가 하나라도 있으면 종료 코드 1로 끝난다. 나중에 워커나 스크립트가 실패를 알 수 있게 한다.
- 처음 설정할 때(초기 적재)도 같은 명령을 쓴다. 2010년 이후 달력일 약 6,000회 호출로, 하루 한도 안에 끝난다.
