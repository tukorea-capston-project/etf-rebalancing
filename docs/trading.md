# 모의·실전투자 설계

KIS Open API로 모의투자·실전투자 주문을 내는 방식을 정의한다. 모드 전환, KIS 자격 증명 보관, 안전장치, 알림을 다룬다.
코드 구현은 `backend/app/trading/`에 둔다. 주문 유형·시각·미체결 처리 등 주문 방식 자체는 #13에서 정한다.

## 전제

- **실제 서비스를 가정한 설계**다. 여러 사용자가 각자 자기 KIS 계좌를 등록해 쓴다고 보고 설계한다.
- 실제로 서비스하지는 않는다(졸업작품). 개발·시연은 팀원 본인 계좌로만 한다.
- 모드, 자격 증명, 정지 상태는 모두 사용자에 속한다. 사용자·인증 설계는 `docs/auth.md`.
- 사용자당 자동 운용 전략은 하나다(`docs/auth.md`).

## 모드

| 모드 | 계좌 | KIS REST | KIS WebSocket |
|---|---|---|---|
| 모의 | 사용자의 KIS 모의투자 계좌 | `https://openapivts.koreainvestment.com:29443` | `ws://ops.koreainvestment.com:31000` |
| 실전 | 사용자의 KIS 실전 계좌 | `https://openapi.koreainvestment.com:9443` | `ws://ops.koreainvestment.com:21000` |

- KIS 주소는 코드 상수(`backend/app/core/config.py`)로 고정하고 모드로 고른다. `.env` 등 설정값으로 주소를 받지 않는다. 그래서 이 두 주소 외에는 쓸 수 없다.
- 백테스트, 모의투자, 실전투자는 같은 리밸런싱 로직을 쓴다(`docs/rebalancing.md`).
- 모드는 사용자 단위로 하나다.

## 모드 전환

사용자가 프론트엔드의 전환 버튼으로 바꾼다. 실전을 언제 시작할지는 사용자가 정한다. 모의투자 검증 기간을 강제하지 않는다.

### 모의 → 실전

백엔드가 아래를 모두 확인해야 전환한다. 프론트엔드 검사만으로 허용하지 않는다.

1. 서버 실전 스위치(`REAL_TRADING_ENABLED`)가 켜져 있다.
2. 사용자의 실전 자격 증명이 등록되어 있고 검증을 통과했다.
3. 사용자가 비밀번호를 다시 입력했다.
4. 사용자가 "실제 돈으로 사람의 승인 없이 자동 주문이 나간다"는 경고를 확인했다.

### 실전 → 모의

- 바로 전환한다. 아직 체결되지 않은 실전 주문은 취소한다.

### 공통

- 전환해도 보유 종목을 옮기지 않는다. 주문할 계좌가 바뀌는 것이므로, 다음 리밸런싱은 새 계좌의 실제 잔고에서 시작한다.
  - 예: 빈 실전 계좌로 전환하면 첫 리밸런싱에서 전략에 정한 금액만큼 목표 비중대로 매수한다.
- 전환 이력(시각, 방향)을 남긴다.

## 자격 증명

### 등록

- 사용자가 모의·실전 각각의 앱키, 시크릿, 계좌번호(앞 8자리 + 상품코드 2자리)를 등록한다. KIS 앱키는 계좌 주인이 KIS 개발자센터에서 직접 발급받는다.
- 등록할 때 접근 토큰을 발급해 보며 검증한다. 발급할 때마다 계좌 주인에게 알림톡이 간다.
- KIS 자격 증명은 `.env`에 두지 않는다. KIS 클라이언트는 자격 증명을 인자로 받고, 설정에서 읽지 않는다.

### 저장

- 앱키, 시크릿, 계좌번호, 접근 토큰은 애플리케이션에서 암호화해 DB에 저장한다(봉투 암호화: 값은 데이터 키로, 데이터 키는 마스터키로 암호화).
- 마스터키는 DB에 두지 않는다. DB가 유출되어도 마스터키 없이는 복호화할 수 없게 하려는 것이다.

| 실행 위치 | 마스터키 | 설정 |
|---|---|---|
| AWS EC2 | AWS KMS. EC2의 IAM 역할로만 쓸 수 있다 | `CREDENTIAL_KEY_PROVIDER=kms`, `KMS_KEY_ID` |
| 팀원 PC(개발·테스트) | `.env`의 로컬 키 | `CREDENTIAL_KEY_PROVIDER=local`, `CREDENTIAL_LOCAL_KEY` |

- 서버 실전 스위치를 켜려면 마스터키가 KMS여야 한다. 로컬 키와 함께 켜면 서버가 시작되지 않는다.
- 공용 개발 DB의 자격 증명은 KMS로 암호화되어 있어 팀원 PC 백엔드에서는 복호화할 수 없다. 팀원 PC에서 KIS를 호출해 보려면 로컬 개발 DB에 자기 모의투자 자격 증명을 등록한다.

### 노출 금지

- 원문을 API 응답으로 돌려주지 않는다. 화면에는 마스킹해 보여 준다(예: `****1234`).
- 로그, 예외 메시지, 알림에 원문을 남기지 않는다. 코드에서는 `SecretStr`로 다룬다.

### 삭제

- 사용자가 삭제하면 즉시 지운다. 캐시된 접근 토큰도 함께 지운다.
- 실전 자격 증명을 지우면 모의로 전환한다(미체결 실전 주문 취소).

### 접근 토큰

- 사용자·모드별로 캐시해 재사용하고 요청마다 새로 발급하지 않는다.
- 유효기간은 1일이고, 재발급은 1분에 1회로 제한되며, 발급할 때마다 알림톡이 발송된다.

## 주문 실행

- 모의·실전 모두 리밸런싱 조건이 되면 **자동으로 주문**한다. 사람의 승인 단계는 없다. 결과는 알림으로 보낸다.
- 금액 상한(투입 금액, 1회 주문 금액)은 두지 않는다. 안전장치는 아래 "안전장치"의 항목이다.
- 주문 유형, 주문 시각, 미체결·부분 체결, 분배금 입금 확인 후 재투자 흐름은 #13에서 정한다.
- 호출 간격을 조절하고, 초당 호출 초과 오류(`EGW00201`)가 나면 재시도한다. 모의투자는 실전보다 호출 제한이 낮다.

## 안전장치

### 서버 실전 스위치

- `.env`의 `REAL_TRADING_ENABLED`. 기본값은 `false`다.
- `false`면 실전 주문을 보내지 않고, 실전 전환도 막는다. 이미 실전 모드인 사용자의 자동 주문은 멈추고 알린다.
- AWS EC2에서만 켠다. 팀원 PC에서는 항상 `false`다.

### 이상 감지 시 주문 중단

주문을 보내기 직전에 검사한다. 하나라도 걸리면 그 회차 주문을 **하나도 보내지 않고**, 그 사용자의 자동 주문을 정지 상태로 바꾼 뒤 알린다. 사용자가 확인하고 재개해야 다시 자동 주문한다.

| 구분 | 검사 |
|---|---|
| 데이터 | 계산일 종가가 없는 보유·목표 ETF가 있다 |
| 전략 | 목표 비중 합계가 100%가 아니거나, 전략 스키마 검증에 실패한다 |
| 계좌 | KIS 잔고(보유 수량, 현금)와 내부 기록이 다르다 |
| 사용자 기준 | 사용자가 정한 기준을 넘는 주문이다 |

- 사용자 기준값은 사용자가 자유롭게 정한다. 서버가 강제하는 최대치는 없다.

### 긴급 중지

- 사용자별 버튼이다. 누르면 그 사용자의 자동 주문을 즉시 멈추고, 미체결 주문을 취소한다. 모의·실전 모두 적용한다.
- 이상 감지와 같은 정지 상태를 쓰고, 정지 사유(이상 감지 / 긴급 중지 / 서버 스위치)를 구분해 남긴다.
- 재개는 사용자가 직접 한다.

## 알림

- 알림 대상: 주문 결과(체결, 미체결), 이상 감지 정지, 긴급 중지, 서버 스위치로 인한 정지, 모드 전환, 접근 토큰 발급 실패.
- 알림에 자격 증명 원문을 넣지 않는다.
