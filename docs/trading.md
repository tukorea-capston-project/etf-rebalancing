# 모의·실전투자 설계

KIS Open API로 모의투자·실전투자 주문을 내는 방식을 정의합니다. 주문 시각·유형·미체결 처리, 모드 전환, KIS 자격 증명 보관, 안전장치, 알림을 다룹니다.
코드 구현은 `backend/app/trading/`에 둡니다.

## 전제

- **실제 서비스를 가정한 설계**입니다. 여러 사용자가 각자 자기 KIS 계좌를 등록해 쓴다고 보고 설계합니다.
- 실제 서비스로 배포할 수 있게 만드는 것이 목표입니다. 개발·시연은 팀원 본인 계좌로 합니다.
- 모드, 자격 증명, 정지 상태는 모두 사용자에 속합니다. 사용자·인증 설계는 `docs/auth.md`를 봅니다.
- 사용자당 자동 운용 전략은 하나입니다(`docs/auth.md`).

## 운용 상태

사용자당 하나인 운용 상태(`docs/auth.md` 소유 관계)에 아래를 둡니다. 전략 버전은 바뀌지 않고, 운용하며 바뀌는 것은 모두 여기와 계좌 기록(아래 "운용 금액과 내부 기록")에 둡니다.

- 운용 중인 전략 버전과 승인한 백테스트
- 모드(모의/실전). 모드는 여기에만 둡니다
- 운용 시작일, 정지 상태와 사유
- 현재 목표 비중, 그때의 국면과 위험자산 비중 기울이기 상태, 전환 이력(`docs/macro.md` 국면 전환)
- 운용 시작·변경·종료·청산과 모드 전환 이력

주문 방식과 주문 전 점검 값은 전략마다 다르지 않은 시스템 규칙이라 정책(`policy.json`의 `trading`)에 둡니다.

## 운용 시작·변경·종료

### 시작

- 승인한 전략 버전으로 시작합니다. 시작한 날을 계산일로 보고 전체 리밸런싱합니다(`docs/rebalancing.md` 시점). 첫 현재 목표 비중은 `docs/macro.md` 운용을 시작할 때를 따릅니다.
- 계좌에 현금만 있어야 시작할 수 있습니다. 종목이 하나라도 있으면 시작하지 않고 이유를 알립니다. 운용 전략 변경, 모드 전환, 종료한 뒤 다시 시작할 때도 같습니다.
  - 사용자가 따로 산 종목이 전략의 평가액·매매·청산에 섞이지 않게 하려는 것입니다. 실전은 계좌 전체를 전략의 돈으로 봅니다(아래 "운용 금액과 내부 기록").
  - 첫 목표 비중을 정할 때 교체 비용을 0으로 보는 전제(`docs/macro.md` 운용을 시작할 때)도 현금에서 사야 맞습니다.
- 내부 보유 기록은 빈 상태에서 시작합니다.

### 변경

- 운용 전략을 다른 전략이나 새 버전(직접 수정 후 백테스트 승인)으로 바꾸려면, 지금 전략을 청산한 뒤 새 전략으로 시작합니다(위 "시작"의 현금만 있는 계좌).
  - 변경을 고르면 아래 "종료와 청산"대로 보유 종목을 모두 팔고, 매도가 모두 끝나 현금만 남은 날 새 전략을 시작합니다.
  - 두 전략에 같은 ETF가 있어도 팔고 다시 삽니다. 시작 조건을 하나로 두어, 사용자가 따로 산 종목이 섞이거나 이전 전략의 보유가 새 전략에 남지 않게 하려는 것입니다.
- 바꾸기 전에 예상 매도 내역과 매매차익 세금을 보여 주고 확인받습니다. 위험회피 국면이면 경고합니다(`docs/macro.md` 위험회피 경고).

### 종료와 청산

- 운용을 종료하면 운용 중인 전략을 비우고 자동 주문을 멈춥니다. 보유 종목과 현금은 계좌에 그대로 둡니다.
- 종료할 때 청산을 함께 고를 수 있습니다.
  - 계좌의 보유 종목을 모두 팝니다. 운용 중인 계좌에는 전략이 산 종목만 있습니다(위 "시작", 아래 "이상 감지 시 주문 중단"의 계좌 검사). 현금은 그대로 둡니다.
  - 확인: 예상 매도 종목·수량·금액과 예상 매매차익 세금을 보여 줍니다. 실전이면 비밀번호를 다시 입력받습니다(모의 → 실전 전환과 같은 수준). 위험회피 국면이면 경고합니다.
  - 주문: 다음 주문 시각(14:30)에 일반 매도와 같은 방식(지정가, 정정, 남은 수량은 다음 영업일)으로 냅니다(아래 "주문 실행"). 이상 감지와 주문 전 점검은 그대로 하되, 사용자 기준(한 회차 매도 금액이 평가액의 N%를 넘음)은 사용자가 직접 요청한 청산에는 적용하지 않습니다.
  - 청산을 고른 뒤에는 리밸런싱·국면 전환 주문을 내지 않고 청산 매도만 냅니다. 주문 시각 전까지 취소할 수 있습니다. 긴급 중지는 청산 주문에도 적용됩니다.
  - 보유 종목이 모두 팔리면 종료가 끝납니다.

## 모드

| 모드 | 계좌 | KIS REST | KIS WebSocket |
|---|---|---|---|
| 모의 | 사용자의 KIS 모의투자 계좌 | `https://openapivts.koreainvestment.com:29443` | `ws://ops.koreainvestment.com:31000` |
| 실전 | 사용자의 KIS 실전 계좌 | `https://openapi.koreainvestment.com:9443` | `ws://ops.koreainvestment.com:21000` |

- KIS 주소는 코드 상수(`backend/app/core/config.py`)로 고정하고 모드로 고릅니다. `.env` 등 설정값으로 주소를 받지 않습니다. 그래서 이 두 주소 외에는 쓸 수 없습니다.
- 백테스트, 모의투자, 실전투자는 같은 리밸런싱 로직을 씁니다(`docs/rebalancing.md`).
- 모드는 사용자 단위로 하나입니다.

## 모드 전환

사용자가 프론트엔드의 전환 버튼으로 바꿉니다. 실전을 언제 시작할지는 사용자가 정합니다. 모의투자 검증 기간을 강제하지 않습니다.

### 모의 → 실전

백엔드가 아래를 모두 확인해야 전환합니다. 프론트엔드 검사만으로 허용하지 않습니다.

1. 서버 실전 스위치(`REAL_TRADING_ENABLED`)가 켜져 있습니다.
2. 사용자의 실전 자격 증명이 등록되어 있고 검증을 통과했습니다.
3. 사용자가 비밀번호를 다시 입력했습니다.
4. 사용자가 "실제 돈으로 사람의 승인 없이 자동 주문이 나간다"는 경고를 확인했습니다.
5. 실전 계좌에 현금만 있습니다(아래 "공통").

### 실전 → 모의

- 모의 계좌에 현금만 있으면 바로 전환합니다(아래 "공통"). 아직 체결되지 않은 실전 주문은 취소합니다.

### 공통

- 전환해도 보유 종목을 옮기지 않습니다. 새 계좌에서 운용을 새로 시작합니다.
- 새 계좌에는 현금만 있어야 합니다(위 "시작"). 종목이 있으면 전환하지 않고 이유를 알립니다.
  - 이전 계좌의 종목은 그대로 남습니다. 나중에 그 계좌로 돌아오려면 그 전에 비워야 하므로, 전환 전에 청산할 수 있게 안내합니다.
- 전환한 날을 운용 시작일로 보고 계산일로 삼습니다. 현재 목표 비중은 그때의 국면으로 새로 정하고(`docs/macro.md` 운용을 시작할 때), 전체 리밸런싱합니다(`docs/rebalancing.md` 시점).
  - 전환 전의 목표 비중은 이전 계좌에서 국면 전환을 거치며 정해진 것입니다. 새로 정해야 목표가 시작한 날의 국면만으로 정해져 백테스트로 재현할 수 있습니다.
  - 다음 리밸런싱 조건까지 기다리면, 예를 들어 분기 주기 전략은 빈 계좌가 몇 달 동안 현금으로 남습니다.
- 내부 보유 기록과 예비금은 계좌별로 둡니다(아래 "운용 금액과 내부 기록").
- 전환 이력(시각, 방향)을 남깁니다.

## 운용 금액과 내부 기록

리밸런싱의 평가액에 넣는 현금(`docs/rebalancing.md` 용어)과 적립금 처리는 모드마다 다릅니다. 리밸런싱 로직은 같고, 전략이 쓸 수 있는 현금을 구하는 방법만 다릅니다.

| 모드 | 전략의 현금 | 적립금 |
|---|---|---|
| 실전 | KIS 계좌 현금 전체 | 사용자가 계좌에 입금합니다. 적립일에는 따로 더하지 않고, 그날의 현금으로 적립금 매수를 합니다 |
| 모의 | KIS 계좌 현금 − 예비금 | 적립일에 예비금에서 적립금만큼 전략의 현금으로 옮깁니다(가상 입금) |

- 실전은 계좌 전체를 그 전략의 돈으로 봅니다. 사용자당 운용 전략도 계좌도 하나라서(`docs/auth.md`) 계좌 잔고가 곧 전략의 포트폴리오입니다.
  - 분배금, 수수료, 세금, 사용자의 입출금은 KIS 현금에 그대로 반영되므로 따로 계산하지 않습니다.
  - 전략에 쓰지 않을 돈은 다른 계좌에 두도록 안내합니다.
  - 시스템은 입금을 따로 구분하지 않습니다. 적립일에 현금 목표를 넘는 현금이 적립금보다 적으면 있는 만큼만 사고, "적립금이 입금되지 않은 것 같습니다"라고 알립니다. 백테스트는 적립금이 들어온다고 가정하므로, 실제 운용이 그 계획과 달라진 것을 사용자가 알 수 있게 하려는 것입니다.
- 모의 계좌는 추가 입금이 안 되고, 처음 잔고가 전략 투자금과 관계없이 정해져 있습니다. 그래서 계좌 현금 중 전략이 쓰지 않는 금액(예비금)을 하나 둡니다.
  - 예비금은 운용을 시작할 때마다(변경, 모드 전환 포함) 다시 정합니다. 그때의 KIS 현금 − 그 전략의 초기 투자금입니다. 예: 모의 잔고가 1억 원, 초기 투자금이 100만 원이면 예비금은 9,900만 원입니다.
    - 시작할 때는 계좌에 현금만 있으므로(위 "시작") 이 식으로 전략의 현금이 정확히 초기 투자금이 됩니다. 한 번만 정하면 다른 초기 투자금의 전략으로 바꿨을 때 이전 전략의 금액으로 운용되어, 그 전략의 백테스트와 금액 조건이 달라집니다.
  - 모의 잔고가 초기 투자금보다 적으면 예비금을 0으로 두고 있는 돈으로 시작하며, 투자금보다 적게 시작한다고 알립니다.
  - 모의 계좌는 사용자가 입출금할 수 없으므로, 그 뒤의 체결·수수료·분배금은 KIS 현금에만 반영되고 예비금은 그대로입니다. 그래서 전략의 현금이 따로 계산하지 않아도 맞습니다.
- 이상 감지(아래 "안전장치")에 쓰는 내부 보유 기록과 예비금은 계좌(사용자·모드)별로 둡니다.
  - 운용을 시작할 때(변경, 모드 전환 포함) 계좌에는 현금만 있으므로 내부 보유 기록은 빈 상태에서 시작합니다(위 "시작").

## 자격 증명

### 등록

- 사용자가 모의·실전 각각의 앱키, 시크릿, 계좌번호(앞 8자리 + 상품코드 2자리)를 등록합니다. KIS 앱키는 계좌 주인이 KIS 개발자센터에서 직접 발급받습니다.
- 등록할 때 접근 토큰을 발급해 보며 검증합니다. 발급할 때마다 계좌 주인에게 알림톡이 갑니다.
- KIS 자격 증명은 `.env`에 두지 않습니다. KIS 클라이언트는 자격 증명을 인자로 받고, 설정에서 읽지 않습니다.

### 저장

- 앱키, 시크릿, 계좌번호, 접근 토큰은 애플리케이션에서 암호화해 DB에 저장합니다(봉투 암호화: 값은 데이터 키로, 데이터 키는 마스터키로 암호화).
- 마스터키는 DB에 두지 않습니다. DB가 유출되어도 마스터키 없이는 복호화할 수 없게 하려는 것입니다.

| 실행 위치 | 마스터키 | 설정 |
|---|---|---|
| AWS EC2 | AWS KMS. EC2의 IAM 역할로만 쓸 수 있습니다 | `CREDENTIAL_KEY_PROVIDER=kms`, `KMS_KEY_ID` |
| 팀원 PC(개발·테스트) | `.env`의 로컬 키 | `CREDENTIAL_KEY_PROVIDER=local`, `CREDENTIAL_LOCAL_KEY` |

- 서버 실전 스위치를 켜려면 마스터키가 KMS여야 합니다. 로컬 키와 함께 켜면 서버가 시작되지 않습니다.
- 서비스 DB의 자격 증명은 KMS로 암호화되어 있어 팀원 PC 백엔드에서는 복호화할 수 없습니다. 팀원 PC에서 KIS를 호출해 보려면 개발 서버를 테스트 DB에 붙이고(`docs/infra.md`) 자기 모의투자 자격 증명을 등록합니다.

### 노출 금지

- 원문을 API 응답으로 돌려주지 않습니다. 화면에는 마스킹해 보여 줍니다(예: `****1234`).
- 로그, 예외 메시지, 알림에 원문을 남기지 않습니다. 코드에서는 `SecretStr`로 다룹니다.

### 삭제

- 사용자가 삭제하면 즉시 지웁니다. 캐시된 접근 토큰도 함께 지웁니다.
- 실전 자격 증명을 지우면 모의로 전환합니다(미체결 실전 주문 취소).

### 접근 토큰

- 사용자·모드별로 캐시해 재사용하고 요청마다 새로 발급하지 않습니다.
- 유효기간은 1일이고, 재발급은 1분에 1회로 제한되며, 발급할 때마다 알림톡이 발송됩니다.

## 주문 실행

- 모의·실전 모두 리밸런싱 조건이 되거나 국면이 바뀌면 **자동으로 주문**합니다. 사람의 승인 단계는 없습니다. 결과는 알림으로 보냅니다.
- 금액 상한(투입 금액, 1회 주문 금액)은 두지 않습니다. 안전장치는 아래 "안전장치"의 항목입니다.
- 최소 주문 금액은 `docs/rebalancing.md` 주문 수량 계산을 따릅니다.
- 호출 간격을 조절하고, 초당 호출 초과 오류(`EGW00201`)가 나면 재시도합니다. 모의투자는 실전보다 호출 제한이 낮습니다.

### 계산과 주문 시각

- 리밸런싱 계산은 계산일 16:00에 합니다(`docs/rebalancing.md` 시점). KRX 데이터는 다음 영업일 아침에 들어오므로(`docs/architecture.md`), 그날 종가는 그 사용자의 접근 토큰으로 KIS 일별 시세를 조회해 받습니다.
  - 국면 판단(`docs/macro.md`)은 다음 영업일 아침 시세 수집이 끝난 뒤 합니다. 국면이 바뀌었으면 16:00에 계산한 결과 대신, 새 현재 목표 비중으로 계산일 종가 기준 전체 리밸런싱을 다시 계산해 주문합니다. 주문 시각까지 KRX 데이터가 들어오지 않아 판단하지 못한 때의 처리는 `docs/macro.md` 국면 판단을 따릅니다.
- 다음 영업일 아침 시세 수집(`docs/market-data.md`)이 끝나면 계산에 쓴 종가를 KRX 종가와 비교합니다. 다르면 주문 전에 KRX 종가로 다시 계산합니다. 주문이 백테스트와 같은 데이터를 쓰게 하려는 것입니다.
  - 주문 시각까지 KRX 데이터가 들어오지 않으면 비교하지 않고 KIS 종가로 계산한 대로 주문합니다.
- 주문은 계산일 다음 영업일 오후, 장 마감 전에 냅니다.

| 시각 | 하는 일 |
|---|---|
| 14:30 | 이상 감지를 하고, 통과하면 매도 주문을 냅니다 |
| 14:30 ~ 14:50 | 매도 체결을 확인하고 남은 수량을 정정합니다. 14:50에 남은 매도는 취소합니다 |
| 매도가 끝난 뒤 | 자금 확인을 하고 매수 주문을 냅니다. 매도가 모두 체결되거나 14:50이 되면 끝난 것으로 보고, 매도가 없으면 14:30에 바로 냅니다 |
| ~ 15:15 | 매수 체결을 확인하고 남은 수량을 정정합니다. 15:15에 남은 매수는 취소합니다 |

- ETF 유동성 공급자(LP)는 장 시작 전 동시호가, 장 시작 후 5분(09:00~09:05), 장 마감 동시호가(15:20~15:30)에 호가를 낼 의무가 없어 가격이 NAV와 벌어질 수 있습니다. 그래서 이 시간에는 주문하지 않습니다.
- 매도 대금은 매도가 체결된 뒤에야 매수에 쓸 수 있습니다. 그래서 매도를 먼저 끝내고 매수합니다.
- 백테스트의 체결 가정(다음 영업일 종가, `docs/backtest.md`)은 그대로 둡니다. 장 마감 전에 주문하므로 실제 체결 가격이 종가와 가깝습니다.

### 주문 유형과 미체결

- 매수·매도 모두 지정가로 냅니다. 매수는 매도1호가, 매도는 매수1호가에 냅니다. 호가가 그대로면 바로 체결되고, 정한 가격보다 나쁘게 체결되지 않습니다.
- 시장가는 쓰지 않습니다. KIS는 가격 없는 주문의 주문 금액을 상한가로 잡으므로, 매도 대금을 거의 다 쓰는 매수(예: 현금 목표 0%)를 한 번에 낼 수 없습니다.
- 체결은 주식일별주문체결조회로 1분마다 확인합니다. 남은 수량(미체결·부분 체결)은 그때의 상대 1호가로 정정하고, 마감 시각(위 표)에 남은 수량은 취소합니다.
  - 주문번호는 직접 보관합니다. 정정·취소 가능 주문 조회 API는 모의투자에서 쓸 수 없습니다.
- 같은 주문을 두 번 보내지 않도록, 주문은 보내기 전에 DB에 "보낼 예정"으로 기록하고 KIS가 받으면 주문번호를 기록합니다. 워커가 주문 도중에 다시 시작하면 "보낼 예정"으로 남은 주문을 주식일별주문체결조회로 대조해, 이미 나간 주문은 다시 보내지 않습니다. 놓친 주문 시각의 처리는 `docs/architecture.md` 놓친 작업을 따릅니다.
- 취소한 수량과 KIS가 거부한 주문(예: 휴장일 YAML이 틀려 장이 닫힌 날, `docs/market-data.md` 미래 영업일 달력)은 다음 영업일 같은 시각에 다시 주문합니다. 백테스트가 거래정지 ETF의 주문을 시세가 다시 생기는 날 체결하는 것과 같은 방식입니다(`docs/backtest.md`).
  - 새 계산이 있는 날에는 넘어온 주문을 버리고 새 계산을 따릅니다. 새 계산은 그날의 잔고에서 시작하므로 남은 차이도 함께 맞춥니다.

### 자금 확인

`docs/rebalancing.md` 주문 수량 계산의 자금 확인은 계산할 때 한 번 하고, 모의·실전투자에서는 매수 주문 직전에 실제 값으로 다시 합니다.

- 매도가 끝나면 매수가능조회의 미수 없는 매수 금액(`nrcvb_buy_amt`)을 확인합니다.
- 매수 총액은 주문 가격 × 수량 × (1 + 수수료율)로 셉니다. 수수료율은 `docs/backtest.md` 비용의 설정값입니다.
- 매수 총액이 미수 없는 매수 금액보다 크면 `docs/rebalancing.md`의 방식대로 매수를 1주씩 줄입니다. 매수를 정정해 가격이 오를 때도 같은 방식으로 확인합니다.
- 미수 없는 매수 금액을 넘는 매수 주문은 내지 않습니다. 증거금 40% 계좌에서는 현금을 넘는 매수가 미수로 체결됩니다.

### 주문 전 점검

이상 감지(아래 "안전장치")를 통과한 뒤, 주문을 내거나 정정할 때마다 ETF별로 확인합니다. 걸린 ETF만 처리하고 자동 주문은 정지하지 않습니다(`policy.json`의 `trading.pre_order_checks`).

- 매수 가격이 NAV보다 1%(잠정) 넘게 비싸면 그 ETF 매수를 보류합니다. 1분마다 다시 확인하고, 15:15까지 풀리지 않으면 다음 영업일로 넘깁니다.
- 거래정지 종목은 건너뛰고 다음 영업일로 넘깁니다.
- 매수 전에는 위 "자금 확인"을 합니다.

### 분배금 재투자

- 매 영업일 아침 기간별계좌권리현황조회로 분배금 입금(ETF, 금액, 입금일)을 확인합니다.
- 입금일 다음 영업일의 주문 시각에 그 금액으로 같은 ETF를 1주 단위로 삽니다. 남는 돈은 현금으로 둡니다. 재투자 규칙은 `docs/rebalancing.md` 분배금을 따릅니다.
- 재투자한 입금은 기록해 두어 두 번 재투자하지 않습니다.

### 보유 ETF가 상장폐지될 때

- 상환금이 계좌에 들어온 날 교체합니다. KIS 잔고에서 그 ETF가 빠지고 상환금이 들어온 것을 확인하면, 내부 보유 기록에서 그 ETF를 먼저 지운 뒤 그날을 계산일로 봅니다. 기록을 먼저 지우지 않으면 이상 감지의 계좌 검사에 걸립니다.
- 새 ETF를 고르고 전체 리밸런싱하는 방법은 백테스트와 같습니다(`docs/backtest.md` 보유 ETF가 상장폐지될 때).
- 상환금이 들어오기 전까지 그 ETF는 시세가 없으므로 거래정지와 같이 다룹니다. 직전 종가로 평가하고, 주문은 다음 영업일로 넘깁니다(아래 "이상 감지 시 주문 중단").
- 백테스트는 마지막 시세일에 바로 현금으로 받으므로, 상환금이 들어오기까지의 며칠만큼 결과가 다를 수 있습니다. 분배금 재투자 시점의 차이(`docs/rebalancing.md` 분배금)와 같은 종류입니다.

## 안전장치

### 서버 실전 스위치

- `.env`의 `REAL_TRADING_ENABLED`입니다. 기본값은 `false`입니다.
- `false`면 실전 주문을 보내지 않고, 실전 전환도 막습니다. 이미 실전 모드인 사용자의 자동 주문은 멈추고 알립니다.
- AWS EC2에서만 켭니다. 팀원 PC에서는 항상 `false`입니다.

### 이상 감지 시 주문 중단

주문을 보내기 직전에, 주문 전 점검보다 먼저 검사합니다. 하나라도 걸리면 그 회차 주문을 **하나도 보내지 않고**, 그 사용자의 자동 주문을 정지 상태로 바꾼 뒤 알립니다. 사용자가 확인하고 재개해야 다시 자동 주문합니다.

| 구분 | 검사 |
|---|---|
| 데이터 | 계산일 종가가 없는 보유·목표 ETF가 있음. 장이 열린 날 특정 ETF만 시세가 없는 경우(거래정지 등)는 빼고 봅니다 |
| 전략 | 목표 비중 합계가 100%가 아니거나, 전략 스키마 검증에 실패함 |
| 계좌 | KIS 잔고의 종목·수량이 내부 기록과 다름. 내부 기록에 없는 종목(사용자가 따로 산 종목 등)이 생긴 경우도 포함합니다 |
| 사용자 기준 | 한 회차 매도 금액 합계가 평가액의 N%를 넘음. 사용자가 직접 요청한 청산에는 적용하지 않습니다 |

- 특정 ETF만 시세가 없으면 정지하지 않습니다. 그 ETF는 직전 종가로 평가하고(`docs/backtest.md` 가격과 체결), 주문은 주문 전 점검에서 다음 영업일로 넘깁니다.
- 현금은 내부 기록과 비교하지 않고 KIS 잔고의 현금을 그대로 씁니다(모의는 예비금을 뺀 값, 위 "운용 금액과 내부 기록"). 실제 수수료, 분배금 입금, 사용자의 입출금 때문에 늘 달라지기 때문입니다. 돈이 모자라는 경우는 자금 확인에서 매수를 줄여 막습니다.
- 사용자 기준은 기본으로 꺼져 있고, 사용자가 켜고 N을 정합니다. 서버가 강제하는 최대치는 없습니다.
  - 기본값을 두지 않는 것은 국면 전환이 사람의 승인 없이 평가액의 절반 넘게 팔 수도 있기 때문입니다. 기본값이 있으면 정상적인 국면 전환도 멈춥니다.

### 긴급 중지

- 사용자별 버튼입니다. 누르면 그 사용자의 자동 주문을 즉시 멈추고, 미체결 주문을 취소합니다. 모의·실전 모두 적용합니다.
- 이상 감지와 같은 정지 상태를 쓰고, 정지 사유(이상 감지 / 긴급 중지 / 서버 스위치)를 구분해 남깁니다.
- 재개는 사용자가 직접 합니다.

### 재개

정지 사유(이상 감지, 긴급 중지, 서버 스위치)와 관계없이 같습니다.

- 정지 중에도 국면 전환으로 현재 목표 비중은 바뀌어 있습니다(`docs/macro.md` 국면 판단). 재개한 날을 계산일로 보고 그때의 현재 목표 비중으로 전체 리밸런싱합니다. 정지 전에 남아 있던 주문은 버립니다.
  - 다음 리밸런싱 조건까지 기다리면, 주기 전략은 정지 중에 바뀐 목표와 다른 상태로 오래 남습니다.
- 계좌 검사(KIS 잔고의 종목·수량 ≠ 내부 기록)로 정지했다면, 재개할 때 차이를 보여 주고 KIS 잔고를 새 내부 기록으로 받아들일지 확인받습니다. 받아들이지 않으면 재개하지 않습니다. 그대로 재개하면 다음 주문 때 같은 검사로 다시 정지합니다.
  - 받아들인 종목 중 현재 목표 비중에 없는 종목은 목표가 0이라 재개한 날의 전체 리밸런싱에서 팝니다. 확인받을 때 이 매도 내역도 함께 보여 줍니다.

## 알림

- 알림은 이메일로 보냅니다.
- 알림 대상: 주문 결과(체결, 미체결), 운용 시작(첫 목표 비중이 전략 비중과 다를 때 그 차이), 국면 전환(어떤 축 점수가 기준을 넘었는지와 기여가 큰 지표, 무엇을 사고팔았는지), 위험회피 경고, 이상 감지 정지, 긴급 중지, 서버 스위치로 인한 정지, 운용 전략 변경, 운용 종료·청산, 모드 전환, 접근 토큰 발급 실패, 모의 운용을 초기 투자금보다 적게 시작함, 적립금이 입금되지 않은 것 같음, 사용자가 지정한 ETF가 선정 조건에서 떨어짐(`docs/strategy-schema.md` 종목 선택 탐색).
- 알림에 자격 증명 원문을 넣지 않습니다.
- 국면 전환 알림은 국면 판단 직후(아침), 주문 전에 "오늘 주문할 내용"으로 보냅니다. 실제 체결은 주문 결과 알림이 따로 알립니다. 사람의 승인은 없지만, 사용자가 주문 전에 내용을 보고 필요하면 긴급 중지를 할 수 있게 하려는 것입니다. 문장을 만드는 방식은 `docs/macro.md` 알림 문장을 따릅니다.

## 미정

- 이메일 발송 수단(SMTP, AWS SES 등)
- 암호화 라이브러리와 로컬 키 형식: 구현 때 정합니다.
- 모의투자에서 기간별계좌권리현황조회를 쓸 수 있는지, 모의 계좌에 분배금이 실제로 들어오는지(#13). 공식 예제에 모의투자 분기가 없어 팀원 모의 계좌로 확인합니다
- 상장폐지된 ETF의 상환이 KIS 잔고·입금 내역에 어떻게 나타나는지(모의투자 포함)
- 실전 자격 증명을 지워 모의로 전환해야 하는데 모의 계좌에 종목이 있어 전환할 수 없을 때의 처리(위 "삭제", 모드 전환 "공통")
