# 사용자·인증 설계

사용자 계정, 로그인 방식, 사용자와 다른 데이터의 소유 관계를 정의함.
코드 구현은 `backend/app/auth/`에 둠.

## 전제

- 여러 사용자가 각자 자기 KIS 계좌를 등록해 쓰는 실제 서비스를 가정해 설계함.
- 실제로 서비스하지는 않는다(졸업작품). 개발·시연은 팀원 계정만 씀.

## 인증 방식

- **서버 세션 + 쿠키**를 씀. 로그인하면 세션을 DB에 저장하고, 세션 ID를 쿠키로 줌.
- 쿠키는 `HttpOnly`, `Secure`로 둠. 서비스가 HTTPS(`*.ts.net` 인증서)로 제공되므로 `Secure`를 쓸 수 있다(`docs/infra.md`).
- 프론트엔드와 API가 같은 오리진에서 서빙되므로 CORS 설정이나 크로스 도메인 쿠키가 필요 없음.
- JWT를 쓰지 않는 이유: 서버가 한 대라 무상태의 이점이 작고, 로그아웃·비밀번호 변경 때 즉시 무효화하려면 결국 서버에 상태를 둬야 함.
- 외부 로그인(OAuth)을 쓰지 않는 이유: 자체 비밀번호가 없으면 실전 전환 때 비밀번호를 다시 입력받는 흐름(`docs/trading.md`)을 만들 수 없음.

## 소유 관계

모드, KIS 자격 증명, 정지 상태, 전략, 포트폴리오는 모두 사용자에 속함.

| 데이터 | 사용자당 개수 | 비고 |
|---|---|---|
| 전략 | 여러 개 | 만들고 백테스트하는 데 제한이 없음 |
| 운용 전략 | **하나** | 계좌에 연결해 자동 주문하는 전략 |
| 모드 | 하나 | 모의 또는 실전 |
| KIS 자격 증명 | 모드별 하나 | `docs/trading.md` |
| 정지 상태 | 하나 | 이상 감지, 긴급 중지, 서버 스위치 |

### 운용 전략을 하나로 제한하는 이유

KIS 계좌는 사용자·모드별로 하나임. 운용 전략이 하나면 계좌 잔고가 곧 그 전략의 포트폴리오이므로, 주문 직전 이상 감지에서 "KIS 잔고와 내부 기록 대조"를 그대로 할 수 있음.
전략 여러 개를 한 계좌에서 운용하려면 보유 수량과 현금을 전략별로 가상 분할해 기록해야 하고, 잔고 대조·분배금 배분·주문 합산이 모두 복잡해짐.

## 미정

- 비밀번호 해시 알고리즘
- 세션 만료 시간, 쿠키의 `SameSite` 값
- CSRF 방어 방식 (쿠키 인증이므로 필요함)
- 실전 전환 시 비밀번호 재입력 흐름의 세부 (재입력 후 유효 시간 등)
- 회원가입 방식 (자유 가입, 초대 등)
- 운용 전략을 바꿀 때 기존 보유 종목을 어떻게 다룰지
