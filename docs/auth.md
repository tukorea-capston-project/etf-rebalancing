# 사용자·인증 설계

사용자 계정, 로그인 방식, 사용자와 다른 데이터의 소유 관계를 정의합니다.
코드 구현은 `backend/app/auth/`에 둡니다.

## 전제

- 여러 사용자가 각자 자기 KIS 계좌를 등록해 쓰는 실제 서비스를 가정해 설계합니다.
- 실제 서비스로 배포할 수 있게 만드는 것이 목표입니다. 개발·시연은 팀원 계정으로 합니다.
- 서비스는 인터넷에 공개됩니다(`docs/infra.md`). 로그인 화면이 누구에게나 열려 있다는 전제로 설계합니다.

## 인증 방식

- **서버 세션 + 쿠키**를 씁니다. 로그인하면 세션을 DB에 저장하고, 세션 ID를 쿠키로 줍니다.
- 쿠키는 `HttpOnly`, `Secure`로 둡니다. 서비스가 HTTPS(CloudFront, 서비스 도메인)로 제공되므로 `Secure`를 쓸 수 있습니다(`docs/infra.md`).
- CloudFront가 정적 파일과 `/api`를 같은 서비스 도메인으로 제공하므로(프론트엔드와 API가 같은 오리진) CORS 설정이나 크로스 도메인 쿠키가 필요 없습니다.
- JWT를 쓰지 않는 이유: 서버가 한 대라 무상태의 이점이 작고, 로그아웃·비밀번호 변경 때 즉시 무효화하려면 결국 서버에 상태를 둬야 합니다.
- 외부 로그인(OAuth)을 쓰지 않는 이유: 자체 비밀번호가 없으면 실전 전환 때 비밀번호를 다시 입력받는 흐름(`docs/trading.md`)을 만들 수 없습니다.

## 소유 관계

모드, KIS 자격 증명, 정지 상태, 전략, 포트폴리오는 모두 사용자에 속합니다.

| 데이터 | 사용자당 개수 | 담는 것 | 바뀌는지 |
|---|---|---|---|
| 전략 버전 | 여러 개 | 목적·기간·금액, 묶음·ETF·전략 비중, 리밸런싱 조건. 버전마다 백테스트 결과와 승인 | 확정하면 바뀌지 않습니다(`docs/strategy-schema.md` 버전 관리) |
| 운용 | **하나** | 운용 중인 전략 버전, 모드(모의/실전), 정지 상태(이상 감지, 긴급 중지, 서버 스위치), 현재 목표 비중과 국면, 전환 이력 | 계속 바뀝니다(`docs/trading.md` 운용 상태) |
| 계좌 기록 | 모드별 하나 | KIS 자격 증명, 내부 보유 기록, 예비금(모의), 주문·체결·분배금 재투자 기록 | 계속 바뀝니다(`docs/trading.md` 운용 금액과 내부 기록) |

- 모드는 운용에만 둡니다. 전략 버전에는 두지 않습니다.
- 시장 상태(국면 지표와 국면 판단)는 사용자에 속하지 않고 시장 전체에 하나입니다(`docs/macro.md`).
- 만들고 백테스트할 수 있는 전략 수에는 제한이 없습니다.

### 운용 전략을 하나로 제한하는 이유

KIS 계좌는 사용자·모드별로 하나입니다. 운용 전략이 하나면 계좌 잔고가 곧 그 전략의 포트폴리오이므로, 주문 직전 이상 감지에서 "KIS 잔고와 내부 기록 대조"를 그대로 할 수 있습니다.
전략 여러 개를 한 계좌에서 운용하려면 보유 수량과 현금을 전략별로 가상 분할해 기록해야 하고, 잔고 대조·분배금 배분·주문 합산이 모두 복잡해집니다.

## 미정

아래 항목은 #17에서 정합니다.

- 비밀번호 해시 알고리즘
- 세션 만료 시간, 쿠키의 `SameSite` 값
- CSRF 방어 방식 (쿠키 인증이므로 필요합니다)
- 실전 전환 시 비밀번호 재입력 흐름의 세부 (재입력 후 유효 시간 등)
- 회원가입 방식 (자유 가입, 초대 등)
- 로그인 시도 제한 (인터넷에 공개되므로 비밀번호 대입 공격을 막아야 합니다)
